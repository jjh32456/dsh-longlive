# 概念：它到底在剪什么（CONCEPTS）

**读完你会得到什么**：能用生活比喻说清「会话日志、token 预算、可见截断、日志截断、六层记忆、`on` 模式」，并明白为什么有些操作必须先把宿主关掉。

## 1. 先认三个词

- **会话日志**：一次对话的完整流水账，文件叫 `session.v4.jsonl.zstd`。它平时是「只追加」的事件流，压缩存放；不是数据库，也不是聊天记录导出。
- **token**：模型计量文字的单位，可以粗略理解成「字数」。你发的、AI 回的、系统塞进去的，都算。
- **上下文窗口 / token 预算**：模型一次能「看见」的 token 上限。就像桌子大小——菜可以很多，但一次只能摆下这么多。

## 2. 为什么聊久了会卡

每问一句，宿主都要把「这次对话里模型还该看见的内容」重新发过去。对话越长，重发的越多。桌子摆满之后：

- 轻则变慢、回答开始不稳；
- 重则请求直接失败（常见 `413`），这一轮就进行不下去。

这不是插件造成的，是长对话的物理上限。插件做的是**在到上限之前，把该收的收掉、该备份的备份**。

## 3. 为什么聊久了会忘

宿主有一个动作叫 **compaction（压缩）**：把前面一大段旧消息压成一段摘要，用摘要替换原文出现在模型面前。原文并没有立刻消失，它还在日志里，只是被「遮住」了（shadowed），模型看不见。

所以「忘」分成两层：

- **模型忘了**：摘要之外的原话不再进入上下文——这是 compaction 的正常代价。
- **磁盘还记着**：旧事件仍占着会话文件的字节，越积越大。

插件不能把模型忘掉的细节变回来；它能做的是：把已经被遮住、永远不会再被模型看见的旧字节回收掉，并且把真正要留的经验写进记忆层。

## 4. 两种「剪」：别混为一谈

| | 日志截断（`session_truncate`） | 可见截断（`session_truncate_visible`） |
| --- | --- | --- |
| 剪什么 | 只剪「已被 compaction 遮住」的旧事件 | 从对话开头按「轮」整段移走 |
| 模型看到 | **一条不少**，可见对话逐字节不变 | 变少（前面的轮次不再发给模型） |
| 界面看到 | 不变 | 变少，开头多一张 `[已归档 ...]` 卡 |
| 原文去哪 | 本来就被遮住，仍可回滚 | `session.v4.jsonl.zstd.archive/<时间戳>.jsonl.zstd` |
| 前提 | **必须先 compact** | 不需要 compact |
| 谁在用 | 手动工具、排障 | 自动截断 runner 走的就是这条 |

**为什么日志截断必须先 compact**：它只能回收「遮住线」之前的字节。没有 compaction 时，计划里的切点只能是 0，一个字节都删不掉；如果绕过它硬砍，可能把已有的 compaction checkpoint（检查点）一起砍掉，遮罩关系失效，下次请求就可能直接爆窗。2026-10-30 有过一次 127 万 token 的 413 事故，教训就是这条。

**可见截断不是删除**：被移走的前缀会归档，原会话另有 `.bak-YYYYMMDD` 备份；真出问题可以盖回去（见 QUICKSTART 第 8 步）。

## 5. 为什么必须「关宿主再剪」

会话日志只有一个写入者：正在运行的那个宿主。它内存里握着事件序号（seq）和写缓冲，还在往下追加。

你一边让它写、一边从中间抽掉一段，就像**边开车边换轮胎**：轻则序号断号、文件尾部撕裂，重则整个会话打不开。所以两个截断工具都会拒绝「当前应用已加载的会话」，报 `VISIBLE_TARGET_IS_LIVE_SESSION`；runner 的做法是先把应用关干净（`CloseMainWindow` → 按 PID 强制结束 → 等 2 秒确认零进程），再剪，再打开。

## 6. 六层记忆：不是六个文件夹，是六种「记法」

这六层是**记忆库**（默认 `%USERPROFILE%\.dsh\longlive-memory`）的组织方式，和聊天记录不是一回事。

| 层 | 像什么 | 落在哪 | 一句话 |
| --- | --- | --- | --- |
| **L1 工作记忆** | 手边桌面 | `.longlive/live/` + `sessions/**` | 当前在聊什么、哪个会话还活着；心跳不是长期记忆 |
| **L2 情景记忆** | 日记 | `journal/YYYY-MM.md` | 这个月发生过什么，按时间串 |
| **L3 语义记忆** | 资料卡 | `topics/*.md` + engram 里的一句 | 稳定的事实、偏好、结论 |
| **L4 程序性记忆** | 操作手册 | `procedures/*.md` | 一件事具体怎么做；目录不存在就是空，不是错误 |
| **L5 索引与召回** | 图书馆目录 | `INDEX.md` 的生成段 + `memory_recall` | 不装内容，只告诉你去哪找 |
| **L6 归档与封存** | 仓库和墓碑 | `epochs/`、`archive/`、`tombstones.md` | 不再常用，但不销毁，留档可查 |

关键点：

- **L1 不是「记忆」**。它是活体状态，进程走了、心跳过期了，就不该再当成事实。
- **L2–L4 是文件**，你可以直接读、直接改；插件只维护格式和索引。
- **L6 是「忘掉」而不是「删掉」**。`memory_forget` 默认 dry-run，真要执行也得给 `confirm: "FORGET"`，卡片会被移到归档并写墓志铭，不删文件。

## 7. `on` 模式是什么，为什么默认不拦

先澄清：`on` **不是截断模式**。截断模式只有 `log` / `dryrun` / `request` 三个；`on` 是另一个开关 `routerRuntime` 的取值（`off` / `shadow` / `on`）。

它像一个**门口的保安**：在工具真正执行前看一眼，只拦写类工具（`memory_save`、`memory_consolidate`、`memory_forget`）里风险高的调用；只读工具（`memory_recall`）永远不拦。拦下时抛 `E_ROUTE_REFUSED`，不会偷偷替你改参数。

那为什么默认 `off`？

1. **默认不改行为**。`off` 时执行路径和没装这个功能时一致，装插件不会突然改变你现有的工作流。
2. **拒绝是不可逆的**。误拒一次，任务就断在那儿；而本版的拒绝路径和误拒率还没有完成充分实测，所以本手册的立场是：**最多开到 `shadow` 观察，不要先开 `on`**。
3. **`shadow` 只记录，不拦**。它把判断写进 `<memoryRoot>/.longlive/router-runtime.jsonl`，返回值原样透传，适合先收集证据。

一句话：`on` 是「高风险写操作的人工闸门」，不是内容审查，也不是沙箱；在它被验证之前，默认不站岗。

## 8. 一次完整的生命周期

```text
你聊完一轮
  → 宿主触发 turn/end
  → 插件估算 token / 轮数
  → 没到阈值：只更新冷却状态，不写日志
  → 到了阈值：
       log     只写一行「我打算怎么剪」
       dryrun  完整算一遍，但不碰会话文件
       request 写一个 request.json，等人来跑 runner
  → runner：关应用 → 可见截断 → 校验 → 重开应用
  → 成功：日志 status=done，request 删除，备份留在会话目录
```

注意两件事：

- **估算是估算**。它按消息 JSON 的体积除以 4 来近似 token，还会把宿主注入的 `user/message` 行算进去；它不是模型的分词器，所以阈值是「安全带」，不是「精密刻度」。
- **阈值有两个条件**：估算 token **≥** `tokensThreshold`，并且轮数 **严格大于** `minTurns`。只满足一个不算。

## 8.1 提案的生命周期（1.1.2）

Router 的写记忆路径是「先提案、后 apply」，所以一条提案是一个有状态的小对象，不是一次性消息：

```text
pending ──approve──→ approved ──apply──→ applying ──→ done
   │                    │                    │
   │                    ├─ lease 被占 / 反复冲突 ──→ blocked-on-user ──超时──→ expired
   │                    └─ 72h TTL ────────────────────────────────────────→ expired
   ├─ reject ──→ rejected
   ├─ cancel ──→ cancelled
   └─ 被同目标小写入合并 ──→ superseded（内容并入 keeper）
```

三条容易误解的规则：

- **`expired` 不删本体**。过期只改状态 + 记一条 `proposal.expired` 审计（带 `bodyKept`），
  提案文件仍留在 `proposals/<id>.json`，你随时能回看当时提了什么、为什么过期。
- **`superseded` 是终态，不是丢失**。同目标、相邻、内容都很短的两条提案会被合并成一条
  （K20 小写入合并）；后一条标 `superseded`，`supersededBy` 指向 keeper，正文已并进 keeper。
  所以它不该再被取消——能取消的是 `cancellable: true` 的行（`pending` / `approved` /
  `blocked-on-user`）。
- **重启不重置视图**。服务启动时以 `proposals/*.json` 为准重建 `proposals/queue.json`
  （审计 `queue.restored`），所以 `list` / `queue` / `status` 三个视图同源，不会出现
  「文件里是 approved、列表里还是 pending」。

## 9. 未来能力（现在还没有）

「过滤器 / scope：按重要度决定哪些内容该记住、哪些该归档」目前只是设计方向，**没有并入本版**；面板里的「过滤器决策」页签在没有数据时显示的是样例。别把它当成已有功能，也别据此做数据规划。

3. 可见截断移走的原文去哪了？
